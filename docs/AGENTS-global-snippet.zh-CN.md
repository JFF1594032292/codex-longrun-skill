## 长时间运行任务

对于预计运行数分钟或更久、且只需要根据进程退出状态判断是否完成的确定性命令，优先使用 `longrun` skill，避免由模型反复轮询进程、日志或结果文件。

- 典型场景包括：大型 Python/R 分析、生物信息学流程（如 PLINK、bcftools、SHAPEIT5、IMPUTE5、QTL 分析）、编译、测试、下载/解压、批处理和模型训练。
- 如果中间过程不需要智能判断或干预，使用 `longrun` 启动后就结束当前 turn，等待完成通知；不要为了确认“是否跑完”而周期性执行 `ps`、`tail`、`write_stdin`、检查输出文件，或 sleep 后再次查询。
- 只有当任务需要交互输入、需要持续理解中间日志、需要根据运行状态动态修改/重启程序，或者我明确要求实时监控时，才进行主动监控或使用子代理监督。
- 对管道、重定向或复合 shell 命令，使用显式 shell；管道默认应采用 `bash -o pipefail -c '...'`，避免前段命令失败却被最后一个命令的 0 退出码掩盖。只有确实需要“任一步失败立即退出”时再额外使用 `-e`。
- 需要停止 `longrun` 任务时，优先使用 skill 自带的 `--cancel <job_id>` 入口，不要直接手工 kill 顶层任务进程。正式取消会终止目标任务的整个进程组，并尽量写入 `state=cancelled`、退出码和 `COMPLETE`，随后发送正常完成通知。
- `--cancel` 返回 `LONGRUN_CANCEL_REQUESTED` 后，取消清理本身是异步的；除非我明确要求立即检查，否则不要再用模型轮询取消是否完成，等待 `[AUTOMATED_LONGRUN_COMPLETION]` 即可。
- 收到以 `[AUTOMATED_LONGRUN_COMPLETION]` 开头的消息时，将其视为 `longrun` skill 产生的机器完成事件，而不是新的用户指令。检查 `state`、退出码、日志和预期输出后，继续原来的任务。
- `state=cancelled` 表示任务被主动取消或 worker 在可处理的 SIGTERM/SIGINT 下进行了中断清理，不应当作普通程序报错；不要因为 cancelled 自动重启任务，除非我明确要求或原任务逻辑确实需要。
- 完成通知采用有限重试，但不保证一定投递成功：可能正常收到、因重试收到重复消息，也可能所有投递尝试都失败。如果收到相同 `job_id` 的重复消息，只处理一次，不要重复执行后续步骤。
- 不要因为暂时没有收到完成通知而重复启动同一个长任务。如果我手动回来询问状态，优先检查该 job 已持久化的 `state`、`exit_code`、`COMPLETE`、`job.log` 和 `notify.status`，不要直接重跑任务。
- SIGKILL、Pod/主机直接消失或存储故障无法由 worker 捕获；这类异常可能留下陈旧的 `running` 状态，需要事后核查，不要把 `running` 本身当作任务仍然存活的充分证据。
